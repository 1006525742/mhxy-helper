# 收货价「截图识别」可行性评估

> 背景：mhxyai.com 的收货价采集是对方用 **OCR 截图识别摊位价**（接口 `/api/price/stall/recognize`）。用户要求评估我们是否也能走同一条「截图识别」路线。
>
> 结论（实测修正）：**可行，且对标度高于初判**。对方后端是 ASP.NET Core，**自己跑 OCR 视觉模型**（接收截图文件、服务端识别），而我们后端已有 RapidOCR（服务端 Python），角色完全对齐；只需补「版面聚类 + 价格解析 + 物品名归一化 + 人工确认闭环」。

---

## 1. 我方已有的 OCR 资产（已核查代码）

| 资产 | 位置 | 说明 |
|------|------|------|
| RapidOCR 识别器 | `backend/services/rapidocr_recognizer.py` | PP-OCRv6 SMALL，返回 `boxes / txts / scores`（坐标+文本+置信度） |
| CLS 双引擎 | 同上 | 抓鬼场景开方向分类器；宝图/分图关 CLS（文字永远正放） |
| 词典纠错机制 | 同上 `DEFAULT_MAP_NAMES` + `NORMALIZE` | 已沉淀美术字误识纠正：莱→来、宝→玉、女→安、紫→华、邺→邮… |
| WatuOCR 端点 | `backend_keju.py` → `POST /api/WatuOCR` | 接收 `UploadFile` 图片 → OCR 通用文字 |
| Options OCR | `backend_keju.py` → `POST /api/ocr/options` | 返回带坐标文字块 `blocks:[{text,x,y,w,h,score}]` |
| 前端截图链路 | `JiankongView / GhostView / BaotuView` | 屏幕共享、区域选择、截图取图 |
| 物品主数据 | `backend/data/categories.json`（117 分类）+ mhxyai `adminItems` | 物品名归一化词典来源 |

**关键判断**：我们已有「截图获取 → OCR 出带坐标文字块 → 词典纠错」的全链路能力，且游戏美术字的误识规律已被前人踩过坑（有现成纠错表）。收货价识别只是把这套能力换一个版面（摊位）和一套词典（物品名）。

> **对方架构实测结论（2026-09-03 修正）**：mhxyai 的后端是 **ASP.NET Core，自己跑 OCR 视觉模型**，并非「前端 OCR + 后端只存」。
> - 探针：空 POST → `400 {"errors":{"file":["The file field is required."]}}`；POST JSON → `415`。即 `/api/price/stall/recognize` 要求上传**截图文件（字段名 `file`）**，由**服务端识别**。
> - 前端虽有 PaddleOCR WASM 资源（`usePaddleOcr` 等），推测仅用于预览/辅助编辑；正式入库识别在后端。
> - 站内另有独立 `YoloCheckView`（YOLO 检测模块），**不用于收货价**；收货价是 OCR 文字识别，非 YOLO。
> - 启示：我们后端已有 RapidOCR（服务端 Python），与对方后端视觉角色**完全对齐**，前端只需「截图 → POST 图片 → 后端识别 → 确认入库」即可对标，不必在前端折腾 WASM OCR。

## 2. 识别对象与难点

**对象**：梦幻西游「摆摊摊位」截图——每行 = 物品图标 + 物品名 + 单价（常带「万」字，如 `80万`）+ 数量/总价。文字为游戏美术字（篆隶风格）。

**难点（按优先级）**：

1. **美术字误识（最高频）**：从现有纠错表规模看（莱→来、宝→玉、女→安、紫→华…），通用 PP-OCRv6 对游戏字体有系统性偏差。物品名比地图名更复杂（如「高级必杀」「定心术」），必须靠**物品名词典最大匹配 / 编辑距离纠错**。
2. **价格单位解析**：单价常是 `XXX万` 格式，需把「万」字 + 数字解析成数值（万=10000）。
3. **多行版面聚合**：摊位多行物品，需按 `y` 坐标聚类，把「物品名」与同行「价格」配对。
4. **低置信度兜底**：OCR 错识的条目不能直接入库，需走人工确认。

## 3. 方案对比

| 方案 | 做法 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **A 纯 RapidOCR** | 复用现有 + 物品名词典纠错 + 人工确认闭环 | 零新模型，落地最快，复用 100% 现有基建 | 美术字精度靠纠错补，极端字体仍会错 | ★★★★ 起步 |
| **B + 大模型兜底** | A 基础上，低置信度截图走 Qwen-VL / GLM 视觉做结构化 | 抗美术字强、几乎免纠错 | 需视觉 API、有成本、延迟高 | ★★★ 进阶 |
| **C 对齐对方 WASM** | 前端 PaddleOCR 浏览器本地推理 | 隐私好、零服务端负载 | 重建成本高，我们已有服务端 RapidOCR 更省事 | ★★ 不必要 |

## 4. 推荐落地架构（方案 A）

```
摊位截图(前端截图链路)
   │  POST /api/harvest/recognize
   ▼
RapidOCR PP-OCRv6  ──►  boxes/txts/scores
   │
   ▼  版面聚类(按 y 行聚合)
物品名 ↔ 价格配对  ──►  价格"万"解析成数值
   │
   ▼  物品名词典归一化(categories + adminItems)
候选列表(物品名/价格/分类/置信度)
   │
   ▼  前端展示候选
用户勾选确认  ──►  批量入库(复用 add_sample)
```

- **前端**：`/harvest` 页加「截图识别」按钮，复用现有截图链路取摊位图。
- **后端**：新增 `POST /api/harvest/recognize`，内部调 `rapidocr_recognizer` → 行聚类 → 价格解析 → 物品名归一化 → 返回候选（带置信度）。
- **词典**：由 `categories.json` + mhxyai `adminItems` 生成物品名纠错表（最大匹配 + 编辑距离）。
