# mhxy-helper 计算器模块可行方案

> 背景：对标市面同类「梦幻西游工具箱」的游戏计算器能力
> 目标：在现有 `mhxy-helper`（Vue 3 + TS + Vite / FastAPI）中加入同能力的计算器模块
> 结论：**可行性高**，计算器属纯前端计算型，可完全复用现有前端栈，无需动 OCR(8001)/游戏(8000) 后端。主要难点是「游戏数据表的准确性与版本维护」，而非工程实现。

---

## 一、参考站分析

### 1.1 定位与规模
- 一个 **梦幻西游数值工具箱**，共 **16 款计算器**，分 4 大类：养成(6) / 装备灵饰(6) / 战斗(2) / 收益(2)。
- 全部为 **纯计算 / 查表** 工具，服务端只托管静态页 + JSON 数据，无实时推理。

### 1.2 全局共性（每个计算器都带）
| 元素 | 说明 |
|------|------|
| 金价 | 梦幻币↔人民币换算基准（顶部全局） |
| 折扣% | 折后价 = 原价 × 折扣 |
| 梦幻币 / 人民币 / 折后 | 三栏联动显示 |
| 数据来源声明 | "基于游戏官方数值与玩家实测整理"，"跟随版本更新维护" |

### 1.5 固伤公式摘要（已抓到官方公式文本，节选）
- **女儿村**：基础固伤 = 敏捷×0.3取整 + 技能²/400 + 技能/2取整；装备总伤 = (武器+灵饰+头盔+龙附+试剑石)×0.5；系数 = 阵法×(法修−法抗)×0.02+1 × (11−目标数×0.1)；点秒 = 基础×系数取整 + 装备总伤×0.5取整 + (法修−法抗)×5 + 神木符。
- **普陀山 / 无底洞 / 阴曹地府 / 盘丝洞 / 天机城**：各自有敏捷系数、技能系数、武器伤害占比、符石/经脉/特殊项，规则各不相同（共 7 套）。
- 这是 16 款里**算法最复杂**的一款，需逐门派实现 + 实测对照校验。

## 二、与现有 mhxy-helper 架构契合度

### 2.1 现有栈（来自 CLAUDE.md / README.md）
- 前端：**Vue 3 + TS + Vite（3000）**，Pinia 状态、service 纯函数层、view 组件、vue-router。
- 后端：**FastAPI（8000 游戏 / 8001 OCR / 8767 物价 wuji）**。
- 数据约定：`frontend/src/data/*.json` 带 `_meta`（version / updated / sources / note），如 `fishingRules.json` 已做「双站逐字校验一致」的元信息记录——**可直接复用到计算器数据**。
- 四件套模式：每功能 = View + Store + Service(s) + 数据 JSON + 路由。
- 首页为 `HomeView.vue` → iframe 嵌入 `/mhxy/static/index.html`（"996长安酒店" 主菜单），新增模块在此加入口。

### 2.2 契合结论
| 维度 | 计算器需求 | 现有能力 | 是否需要新增 |
|------|-----------|----------|--------------|
| UI/表单 | 输入→实时计算 | Vue 组件齐全 | 仅需少量通用输入组件 |
| 计算 | 纯函数公式/查表 | service 层模式成熟 | 复用，每计算器一个 service |
| 数据 | 游戏数值表(JSON) | `src/data/*.json` 约定 | 复用，新增各表 + `_meta` |
| 金价换算 | 梦幻币↔人民币 | **wuji 物价后端(8767) 已存在** | 接入 wuji 或直接手动输入 |
| OCR/截图 | 无 | 现有 | 不需要 |
| 后端推理 | 无 | 现有 | 不需要 |

**结论**：计算器模块 100% 可走**纯前端**路线，挂在现有 Vite 下，复用 router/store/service/data 范式，仅与 wuji(8767) 在「金价/物价」上做可选集成。

## 三、可行技术方案

### 3.1 模块目录（新增，不影响现有功能）
```
frontend/src/
├── calculators/
│   ├── engine/                 # 共享计算引擎（纯函数）
│   │   ├── money.ts            # 梦幻币↔人民币换算（金价/折扣）
│   │   ├── levelTables.ts      # 等级→消耗表 通用工具
│   │   ├── format.ts           # 数值/单位格式化（万/亿、元）
│   │   └── types.ts            # 通用类型
│   ├── services/               # 每个计算器一个纯函数 service
│   │   ├── masterSkill.ts
│   │   ├── cultivation.ts
│   │   ├── gemSynthesis.ts
│   │   ├── fixedDamage.ts      # 7 门派分支
│   │   └── ...
│   ├── data/                   # 游戏数值表（带 _meta）
│   │   ├── masterSkill.json
│   │   ├── gemSynthesis.json
│   │   └── ...
│   ├── components/             # 可复用表单组件
│   │   ├── LevelInput.vue      # 等级滑块/输入
│   │   ├── PriceBar.vue        # 金价/折扣/三栏联动（全局）
│   │   ├── CostTable.vue       # 结果表（万/亿/元）
│   │   └── SelectMenu.vue      # 门派/套装下拉
│   └── views/
│       ├── CalculatorHome.vue  # 16 款总览（4 分类宫格）
│       └── CalcXxxView.vue     # 每款一个（懒加载）
├── stores/
│   └── priceStore.ts           # 全局金价/折扣（持久化 localStorage）
└── router.ts                   # 新增 /calc, /calc/:name
```

### 3.2 计算放前端还是后端？
- **推荐纯前端**：所有计算为确定性的公式/查表，无外部依赖、无隐私、可离线。与同类工具站的实现方式一致。
- 后端仅在「金价/物价」上可选使用 wuji(8767) 的实时价格；否则用户在 `PriceBar` 手动填金价即可（最简 MVP）。
- 若未来要「云端存档/多端同步」，再加一个轻量 FastAPI + SQLite 即可，**不是首期范围**。

### 3.3 关键引擎设计（示例）
```ts
// engine/money.ts —— 全局金价换算（复用 wuji 或手动）
export function toRMB(mhxyWan: number, goldPrice: number, discount = 1): number {
  // goldPrice: 元 / 3000万梦幻币；万→元 = 万 / 3000 * goldPrice
  return (mhxyWan / 3000) * goldPrice * discount
}

// services/gemSynthesis.ts —— 纯函数，输入等级返回成本表
export function gemSynthesis(level: number, gemPrice1: number): GemRow[] { /* ... */ }

// services/fixedDamage.ts —— 7 门派分支
export function fixedDamage(school: School, input: FxInput): FxResult {
  switch (school) {
    case '女儿村': return calcNeCun(input)
    case '普陀山': return calcPuTuo(input)
    /* ... 7 分支 ... */
  }
}
```

### 3.4 数据表维护策略（最关键）
参照现有 `fishingRules.json` 的 `_meta` 做法，每个数据 JSON 必须带：
```json
{
  "_meta": {
    "version": "1.0.0",
    "updated": "2026-08-10",
    "sources": ["官方数值", "玩家实测"],
    "note": "与真值表同输入对比一致；版本更新需重校",
    "crossCheck": "与参考站 5 组样本误差 < 0.1%"
  }
}
```
- 每加一张表，写**对照校验脚本**（与真值表同输入核验），纳入 CI/本地校验，防止版本漂移。
- 固伤/乱敏需额外「官方公式 + 实测录像」双源校验。

## 四、可行性与风险

| 项 | 评估 |
|----|------|
| 工程可行性 | **高**。纯前端，无新基础设施；复用现有四件套范式 |
| 数据准确性（最大风险） | 中–高。依赖官方/实测数值，需建立「来源标注 + 对拍校验」流程 |
| 固伤/乱敏算法 | 中–高。公式复杂（7 门派），需逐门派实现 + 实测对照 |
| 物价/金价时效 | 低–中。手动填金价即可 MVP；接 wuji(8767) 可更准 |
| 工作量 | 16 款 ×（service+view+data）≈ 中–大，但同质化高，可模板化批量产出 |
| 不需要的能力 | OCR、屏幕共享、后端推理、模型——一律不涉及 |

## 五、实施路线（分阶段，建议 4 期）

**Phase 0 — 脚手架（0.5–1 人日）**
- 新增 `calculators/engine`、`PriceBar`、`LevelInput`、`CostTable` 组件；`priceStore`；`/calc` 路由 + `CalculatorHome` 总览页；在首页 index.html 加入口。
- 写好 `money.ts` / `format.ts` 通用引擎 + 对拍校验骨架。

**Phase 1 — 公式/合成型（低难度，高价值，约 3–4 人日）**
- 师门技能、人物修炼、召唤兽修炼、帮派技能、宝石合成、星辉石/钟灵石/五色灵尘合成（共 8 款，模式同质）。
- 产出：每款 service(纯函数) + view + data JSON + 对拍脚本。

**Phase 2 — 查表/推荐型（约 2 人日）**
- 符石组合、动物套选择（查表 + 规则推荐）。

**Phase 3 — 分析/门派型（难度高，约 3–4 人日）**
- 固伤（7 门派公式）、乱敏（概率分布）、底子提升、体活计算、庭院收益、口袋幻境倒卖。
- 庭院/口袋依赖物价数据 → 接入 wuji(8767) 或内置简化物价表。

**验收标准**：每个计算器与真值表同输入核验，误差 < 0.1%（货币类）/ 完全一致（离散类）。
